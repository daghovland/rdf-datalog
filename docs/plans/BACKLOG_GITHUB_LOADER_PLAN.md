# Backlog GitHub loader — plan

Implements [#284](https://github.com/daghovland/rdf-datalog/issues/284)
(sub-issue of epic [#282](https://github.com/daghovland/rdf-datalog/issues/282),
depends on [#283](https://github.com/daghovland/rdf-datalog/issues/283) —
merged). Working branch: `feat/284-backlog-github-loader`.

## Goal

A one-shot "regenerate the whole snapshot" loader: fetch this repo's current
issue/PR/label state from the GitHub API, materialize it as `bl:`-vocabulary
RDF quads in a `Datastore` (per
[`backlog/ontology/vocabulary.ttl`](../../backlog/ontology/vocabulary.ttl)),
and serialize to a checked-in `.ttl` snapshot. No incremental/diff logic —
that's deferred to the write-back sub-issue
([#287](https://github.com/daghovland/rdf-datalog/issues/287)), per the
issue's own resolved open question.

## Crate structure

New workspace member `backlog/` (added alongside the pre-existing
`backlog/ontology/`, `backlog/examples/`, `backlog/queries/` directories —
`backlog/Cargo.toml` sets `autoexamples = false`, `autotests = false`,
`autobenches = false` so Cargo doesn't try to treat the existing `.ttl`/
`.sparql` fixtures as build targets):

```
backlog/
├── Cargo.toml          (autoexamples/autotests/autobenches = false)
├── src/
│   ├── lib.rs           re-exports
│   ├── model.rs         RawIssue / RawLabel — the GitHub API response shape actually used
│   ├── github.rs        GitHubSource trait + GhCliSource (shells to `gh api`) + FixtureSource (test double)
│   ├── crates.rs        parses root + member Cargo.toml files -> CrateInfo (name, path, path-deps)
│   └── loader.rs         build_snapshot(issues, pr_files, crates) -> Datastore
├── tests/
│   ├── fixtures/*.json   trimmed real `gh api` responses (recorded, not live)
│   └── loader_test.rs
```

`snapshot.ttl` (the checked-in output) lives at
`backlog/examples/snapshot.ttl` — generated by a small `bin/regenerate.rs`
that does live `gh api` calls (not exercised by the test suite).

## GitHub API calls, and why

1. **Issues + PRs**: `gh api --paginate --jq '.[]' "repos/{owner}/{repo}/issues?state=all&per_page=100"`.
   GitHub's Issues API returns PRs too (a PR is an issue with a
   `pull_request` field present) — one call covers both `bl:Issue` and
   `bl:PullRequest` sources. `--jq '.[]'` flattens each page's array into
   one JSON object per line (NDJSON), which `serde_json::Deserializer`'s
   stream API parses without needing `--slurp`.

2. **Sub-issue relationships**: read directly off each issue's own
   **`parent_issue_url`** field (present on every issue returned by call 1,
   e.g. `https://api.github.com/repos/.../issues/267`) rather than making a
   second per-parent call to `.../issues/{number}/sub_issues`. Both surface
   the same native GitHub sub-issue relation; `parent_issue_url` gives it
   from the child's own listing with zero extra API calls (no N+1 fan-out
   over every issue), where `/sub_issues` would require one call per
   *parent* candidate to discover children. Verified against real data
   (`gh api repos/daghovland/rdf-datalog/issues/258 -q .parent_issue_url`
   returns `.../issues/267`, matching the hand-authored fixture). The
   issue number is parsed off the trailing path segment of that URL.

3. **PR changed files** (for `bl:touchesCrate` on PRs only — see "Scope
   deliberately narrowed" below):
   `gh api repos/{owner}/{repo}/pulls/{number}/files --jq '.[].filename'`,
   one call per PR. Each filename's leading path segment is matched
   against the crate directory list from call 4 below.

4. **Crate dependency graph**: **no GitHub call** — read straight from the
   checked-out repo's own `Cargo.toml` files (root workspace `members` list,
   then each member's `[dependencies]` table for path deps), per
   `vocabulary.ttl`'s own comment on `bl:dependsOnCrate` ("read straight off
   the dependent crate's own Cargo.toml ... to avoid a second source of
   truth"). Only `[dependencies]`, not `[dev-dependencies]` — matches the
   hand-authored `crates_and_dependencies.ttl` fixture (e.g. `dagalog`
   there omits `shacl`/`jsonld_parser`/`rdf_canon`, which are dev-only).

## Field mapping

| GitHub field | `bl:` triple |
|---|---|
| `html_url` | subject IRI (used as-is, already `.../issues/N` or `.../pull/N`) |
| `title` | `rdfs:label` (no bespoke `bl:title` — vocabulary convention) |
| `number` | `bl:number` (xsd:integer) |
| `state` (`open`/`closed`) | `bl:state` → `bl:Open`/`bl:Closed` |
| `labels[].name` | `bl:hasLabel` → `bl:<Name>` label resource (minted with `a bl:Label ; rdfs:label "<raw name>"` if not already one of the vocabulary's named individuals `bl:Bug`/`bl:Enhancement`/`bl:Ready`) |
| `pull_request` present? | `a bl:PullRequest` vs `a bl:Issue`, plus `a bl:WorkItem` always (see MODELING_NOTES "`rdfs:subClassOf` is not free" — this engine does no RDFS inference at query time, so every level needs an explicit type triple) |
| `parent_issue_url` | `bl:subIssueOf <parent>` (issues only) |
| computed: has `parent_issue_url` == null AND is the parent of >=1 other issue | `a bl:Epic` (derived, not fetched — matches MODELING_NOTES's "asserted by the loader when it materializes an issue that currently has sub-issues and no parent") |
| body text, PR: `Closes/Fixes/Resolves #N` (case-insensitive, singular/plural/past-tense) | `bl:closesIssue` — but only if `#N` resolves to something typed `bl:Issue` in the same fetched set, never a PR number |
| body text, any other bare `#N` mention | `bl:relatesToIssue`, **minus** anything already asserted as `bl:closesIssue` (so a body reading "Closes #161 ... see also #161" doesn't assert both) |
| `bl:hasLabel bl:Ready` | also assert `bl:status bl:Ready` (only for `bl:Issue`, never `bl:PullRequest` — `bl:status`'s domain) — per vocabulary's explicit instruction to derive, not double-assert, since `bl:Ready` is intentionally both a `bl:Label` and a `bl:WorkflowStatus` |
| PR's changed file paths (call 3) | `bl:touchesCrate` on that PR, one triple per distinct crate directory touched |
| Cargo.toml `[dependencies]` path entries | `bl:dependsOnCrate` |

### Deliberately out of scope for this loader (documented, not silently dropped)

- **Issue body text is not persisted.** There is no `bl:body`/description
  property in `vocabulary.ttl` — MODELING_NOTES.md ("The #285 shape
  library") already flags this as a deliberately-minimal v1 gap, to be
  revisited only if a real need for it shows up. Inventing a bespoke
  property here would repeat the exact mistake `rdfs:label`-for-title was
  designed to avoid. Body text IS read (needed to extract `#N`
  closes/relates references), just not stored as its own triple.
- **`bl:touchesCrate` on issues** (as opposed to PRs) is not computed. The
  vocabulary's own comment allows it ("or, for a still-open issue, is
  expected to change") but there's no reliable GitHub-API-derivable signal
  for "expected" crate impact on an open issue — the two fixture cases that
  have it (#264, #266) were hand-annotated. Left for a human/label
  convention to define later, tracked informally here (no separate issue
  filed since it's a documented narrowing of #284's own stated scope, not a
  new gap).
- **`bl:status bl:InProgress`/`bl:Done`** are not derived. `InProgress` has
  no GitHub label in this repo (branch-name-comment convention only, per
  MODELING_NOTES) and `Done` isn't a straightforward GitHub-API field
  either. Only the `Ready` label → `bl:status bl:Ready` derivation
  (explicitly called out in the vocabulary) is implemented.

## Testing strategy

All unit/integration tests run against **recorded fixture JSON**
(`backlog/tests/fixtures/*.json`, trimmed real `gh api` output for a
representative slice: an epic with children (#267/#258), a mid-tree case,
a PR with `Closes #N` (#276→#258), the #292/#161 mention-without-closing
case, an issue with two labels, a couple of crates) via `FixtureSource`, a
`GitHubSource` test double — never live network calls. One
`#[ignore]`-marked live smoke test (`tests/live_smoke.rs`) hits the real
API for a sanity check, run manually, never in CI.

The acceptance test for the *generated* snapshot loads
`vocabulary.ttl` + `shapes.ttl` + the loader's output through this repo's
own `shacl` crate, mirroring `tests/backlog_ontology.rs`'s existing
pattern — this catches structural mistakes (missing `bl:WorkItem` type,
Epic wrongly carrying `bl:subIssueOf`, etc.) that fixture-assertion tests
alone would miss. The full live snapshot is expected to still surface the
two known pre-existing structural gaps documented in
`real_gap_standalone_issue_274.ttl` (some real issues have no epic parent)
— that's a backlog-data fact, not a loader bug, and is not asserted to
conform.

## Output stability

`turtle::serialize_graph` emits N-Triples-shaped Turtle (fully expanded
IRIs, no prefixes) in quad-storage iteration order, which is not a
stability guarantee. The snapshot writer sorts serialized lines before
writing so the checked-in file doesn't reshuffle on every regeneration run
(diff noise).
