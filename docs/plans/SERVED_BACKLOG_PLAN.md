# A served, GitHub-independent backlog + provenance system — plan

## Context: what was decided before, and what's being reconsidered

The backlog epic (#282) started from a deliberate constraint, stated in its
own issue body:

> Per the existing "Github backlog" policy in CLAUDE.md, issue/epic status
> lives in GitHub Projects, not in local files. This project must not
> invert that: the RDF graph is a **derived, resyncable snapshot** pulled
> from the GitHub API, not a new source of truth.

That constraint shaped everything built since: the `bl:` vocabulary models
GitHub's own concepts fairly literally (issue/PR/label/open-closed state),
the loader (#284) is a one-shot "regenerate from the GitHub API" pull, and
#287 (still open, not started) was scoped as "diff local RDF edits against
the last pull, translate the diff into safe GitHub API mutations" — i.e.,
GitHub-bound in both read and (eventually) write directions.

**Reconsideration (repo owner, 2026-08-02):** long-term, bind the served
backlog+provenance system less tightly to GitHub's own representation.
Direct quote: *"I would like to plan for the whole backlog stuff to become
something that is served and represents both issues, history and
everything. This is also an input for 287, which is not that exciting
given I would like to long-time create something separate, and binding to
github representation might set un-necessary boundaries."*

This does NOT mean rip out GitHub today — it's still where issues actually
get triaged, labeled `ready`, and merged day-to-day, and #284's loader is
genuinely useful as-is. It means: **don't let GitHub's specific data model
become the ceiling on what the served system can represent or do**,
especially now that provenance (#306) has added a second kind of history
(reasoning/decisions) that has no GitHub-native equivalent at all — it was
never going to fit "mirror GitHub's issue tracker" cleanly to begin with.

## What "served" means here

Not just "SPARQL-queryable from a checked-in `.ttl` file via a one-shot CLI
re-parse" (today's pattern for both `backlog/` and `provenance/`). A
persistent process — most naturally `sparql_endpoint`'s existing `--serve`
HTTP mode, already a full SPARQL 1.1 Protocol endpoint — kept running,
backed by a `Datastore` that's populated from (at least, to start):

- The GitHub-derived backlog snapshot (#284's loader output) — refreshed
  periodically, not just regenerated by hand on demand.
- The provenance graph (`agp:`/`bl:` — transcript summaries, decisions,
  sessions).
- Whatever `provenance/summaries/` (backfilled per #352/#355) and future
  `backlog/`-adjacent data accumulates over time.

This turns "run a canned query script against some files" into "there's a
live SPARQL endpoint you can point any tool at" — a real dogfood of
`sparql_endpoint` itself, not just `dag_rdf`/`shacl`/`turtle` (echoing
#282's original stated dogfooding goal, just extended to the serving layer
too).

## Why "GitHub-independent" matters going forward, concretely

1. **Provenance never fit the GitHub model to begin with.** `agp:` already
   models things GitHub has no concept of (an `agp:AgentSession`, a
   `agp:Decision` with rejected alternatives) — it was always adjacent to
   `bl:`, not a natural extension of it. The served system is already, in
   practice, more than "a GitHub mirror."
2. **#287, reframed.** Instead of "the served system needs a write-back
   path to GitHub to be complete," treat GitHub sync (in either direction)
   as *one integration among possibly several*, not the design's organizing
   principle. A served system that's independently useful (query your own
   backlog+provenance history) doesn't NEED write-back to be valuable — the
   original epic's phasing (read/query first, defer write-back, "the
   riskier, genuinely novel half") already hedged this correctly; this just
   makes the hedge more permanent rather than assuming #287 is inevitable.
3. **Room to model things GitHub doesn't have**, if it ever becomes useful
   (e.g., work items that aren't GitHub issues at all, richer workflow
   states than GitHub's label-based ones, cross-repo backlog if `backlog/`
   really does graduate into its own repo as #282 already anticipated).
   Not designing any of this now — just not foreclosing it by treating
   GitHub's schema as the system's permanent shape.

## What NOT to do now (avoid over-engineering ahead of real need)

- Don't redesign `bl:`/`agp:` vocabulary today — nothing about the current
  schema is actually blocking anything; this is a stance on future design
  center, not a rewrite trigger.
- Don't build a permanently-running server today either — the near-term,
  concrete step is smaller (see below); "always-on service" can follow once
  there's enough data/usage to justify it.
- Don't treat this as canceling #287 — it stays open, just explicitly
  reframed (see below) as optional-integration rather than core-path.

## Concrete near-term steps

1. **Comment on #287** noting this reconsideration directly, so whoever
   picks it up later designs write-back (if it's ever built at all) as an
   optional sync integration, not something the served system's core design
   depends on.
2. **New tracked issue** (this plan's actual deliverable, filed alongside
   this doc): stand up `sparql_endpoint --serve` against a combined
   backlog+provenance dataset, refreshed periodically from #284's loader
   output plus whatever's in `provenance/summaries/`. Concrete open
   questions to resolve in that issue, not here:
   - Refresh mechanism: cron-style periodic re-run of the loader + reload,
     vs. a GitHub webhook triggering refresh, vs. manual/on-demand for now.
   - Where it actually runs (this Hetzner box, alongside everything else
     already running here, vs. somewhere dedicated) — low stakes either way
     at current scale, but worth deciding explicitly rather than defaulting
     silently.
   - Whether "served" initially just means "reachable from this box's own
     tooling" (agents/scripts querying `localhost`) or genuinely
     externally reachable — start with the former, the latter raises its
     own auth/exposure questions out of scope for this plan.
